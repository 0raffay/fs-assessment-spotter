# Deployment (Render + Vercel)

The API runs on **Render** (a Python web service) and the frontend on **Vercel** (static files).
The browser loads the app from Vercel and calls the API on Render directly. CORS allows that one
origin. HERE and Open-Meteo are only ever called by the API, so keys never reach the browser.

```
browser ──► Vercel (apps/web/dist: HTML, JS, CSS)
   │
   └─────► Render: skyrig-api (Django + gunicorn) ──► HERE (routes, geocode)
                                                   └► Open-Meteo (weather)
```

Deploy the **API first** (the frontend needs its URL), then the **frontend**, then tell the API the
frontend's URL (CORS).

## Before you start

- The repository is on GitHub (`main` pushed).
- A **HERE API key**: [platform.here.com](https://platform.here.com) → Access Manager → Apps →
  API Keys.
- Free accounts on [render.com](https://render.com) and [vercel.com](https://vercel.com), each
  connected to GitHub.

## 1. API on Render

The repo has a Blueprint, [`render.yaml`](../render.yaml), which defines the service: build and
start commands, health check and environment.

1. Render dashboard → **New** → **Blueprint** → choose this repository → **Connect**.
2. Render reads `render.yaml` and asks for the values marked `sync: false`:

   | Variable               | Value                                                                                          |
   | ---------------------- | ---------------------------------------------------------------------------------------------- |
   | `HERE_API_KEY`         | Your HERE key                                                                                  |
   | `CORS_ALLOWED_ORIGINS` | Leave as `https://example.com` for now; you'll set the Vercel URL in step 3                    |
   | `DJANGO_ALLOWED_HOSTS` | Leave empty. Render's own host name (`skyrig-api-xxxx.onrender.com`) is allowed automatically. |

   `DJANGO_SECRET_KEY` is generated by Render, and the rest is fixed in the Blueprint
   (`DJANGO_SETTINGS_MODULE=config.settings.prod`, `SKYRIG_PROVIDERS=live`, Python 3.11.9).

3. **Apply**. The first build takes a few minutes:

   ```
   pip install uv
   uv sync --frozen --no-dev
   python manage.py collectstatic --noinput
   python manage.py migrate --noinput
   ```

   Then the service starts with:

   ```
   gunicorn config.wsgi:application --workers 1 --threads 8 --timeout 60
   ```

4. Check it. Copy the service URL from the dashboard (e.g. `https://skyrig-api-xxxx.onrender.com`):

   ```bash
   curl https://skyrig-api-xxxx.onrender.com/api/health/
   # {"status":"ok"}
   curl "https://skyrig-api-xxxx.onrender.com/api/geocode/?q=Dallas"
   # {"results":[{"id":"geonames:dallas-tx-…","name":"Dallas","region":"TX",…}]}
   ```

> **Why one worker?** Forecasts, finished heatmaps and each plan's corridor are cached in memory.
> With one gunicorn process (and 8 threads) every request sees the same cache. To run more
> workers, add Redis: create a Render Key Value instance, set `CACHE_URL` to its URL, and add the
> `redis` package (`uv add redis`).

## 2. Frontend on Vercel

1. Vercel dashboard → **Add New** → **Project** → import this repository.
2. Configure the project:

   | Setting          | Value                                                         |
   | ---------------- | ------------------------------------------------------------- |
   | Root Directory   | `apps/web`                                                    |
   | Framework Preset | Vite (from [`apps/web/vercel.json`](../apps/web/vercel.json)) |
   | Build Command    | `pnpm build` (from `vercel.json`)                             |
   | Output Directory | `dist` (from `vercel.json`)                                   |

   Vercel finds the pnpm workspace from the root `pnpm-lock.yaml` and installs with pnpm.

3. Environment variables (Production, and Preview if you use preview deployments):

   | Variable            | Value                                               |
   | ------------------- | --------------------------------------------------- |
   | `VITE_API_BASE_URL` | `https://skyrig-api-xxxx.onrender.com/api`          |
   | `VITE_ENABLE_MOCKS` | `false` (already the default for production builds) |

   `VITE_*` values are baked in at build time. After changing one, redeploy.

4. **Deploy**. Note the production URL, e.g. `https://skyrig.vercel.app`.

`vercel.json` rewrites unknown paths to `index.html` (client-side routing), and caches the
fingerprinted `/assets/*` files for a year.

## 3. Connect them (CORS)

1. Render → `skyrig-api` → **Environment** → set `CORS_ALLOWED_ORIGINS` to the Vercel URL,
   exactly, with no trailing slash:

   ```
   https://skyrig.vercel.app
   ```

   For several origins (a custom domain too), separate them with commas.

2. Optional, for Vercel **preview** deployments, whose URLs change each time: add
   `CORS_ALLOWED_ORIGIN_REGEXES`, for example:

   ```
   ^https://skyrig-[a-z0-9-]+-your-team\.vercel\.app$
   ```

3. **Save**. Render redeploys with the new value.

## 4. Check the deployment

- [ ] `https://<api>/api/health/` returns `{"status":"ok"}`.
- [ ] Opening the Vercel URL shows the planner. The status in the header reads "No trip planned
      yet".
- [ ] Typing "Dal" in **From** lists Dallas, TX. Typing a ZIP (`80202`) lists a HERE result.
- [ ] Planning Dallas → Denver returns three routes with checkpoints, and the browser's network
      tab shows `POST https://<api>/api/routes/plan/ 200`, not a mock.
- [ ] The forecast timeline loads (`GET …/api/weather/heatmap/?…&planId=… 200`), and the slider
      moves the heatmap.
- [ ] Share copies a link that opens the same trip in a new tab.

## Environment reference

**API (Render)**

| Variable                      | Required | Default                | Notes                                                                |
| ----------------------------- | -------- | ---------------------- | -------------------------------------------------------------------- |
| `DJANGO_SETTINGS_MODULE`      | yes      | `config.settings.prod` | Set by the Blueprint (also `wsgi.py`'s default)                      |
| `DJANGO_SECRET_KEY`           | yes      | generated              | Never reuse the dev key                                              |
| `HERE_API_KEY`                | yes      | —                      | Routing and geocoding of ZIPs and addresses                          |
| `CORS_ALLOWED_ORIGINS`        | yes      | —                      | The frontend's origin(s)                                             |
| `CORS_ALLOWED_ORIGIN_REGEXES` | no       | —                      | Patterns, e.g. for Vercel previews                                   |
| `DJANGO_ALLOWED_HOSTS`        | no       | Render's host is added | Extra host names, e.g. a custom API domain                           |
| `CSRF_TRUSTED_ORIGINS`        | no       | —                      | Only for the Django admin over a custom domain                       |
| `CACHE_URL`                   | no       | in-memory              | `redis://…` to share the cache across workers                        |
| `SKYRIG_PROVIDERS`            | no       | `live`                 | `fake` runs on offline data, which is handy for a demo without a key |
| `DJANGO_LOG_LEVEL`            | no       | `INFO`                 | Provider failures are logged as warnings                             |

**Frontend (Vercel, build time)**

| Variable            | Required | Default                      | Notes                        |
| ------------------- | -------- | ---------------------------- | ---------------------------- |
| `VITE_API_BASE_URL` | yes      | `/api`                       | Full URL of the API's `/api` |
| `VITE_ENABLE_MOCKS` | no       | `false` in production builds | `true` serves fake data      |

## Free-tier notes

- **Render sleeps after ~15 minutes idle.** The next request wakes it, which can take about a
  minute, longer than the app's 30-second request limit, so that first plan may fail with "The
  server took too long". Before a demo, open `https://<api>/api/health/` once and wait for
  `{"status":"ok"}`. A paid instance doesn't sleep.
- **Open-Meteo's free tier:** about 600 locations a minute and 10,000 a day. Each location counts
  as one call. A long trip's plan plus heatmap uses a few hundred, so many trips in a row can hit
  the limit. The app then shows "Forecast unavailable … busy (free-tier limit)" with a Retry
  button. Caching (30 minutes) and corridor-only heatmaps keep normal use well inside the limit.
- **HERE's free tier** covers this project's use (a few calls per plan).

## Troubleshooting

| Symptom                                                            | Cause and fix                                                                                       |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| Browser console: "blocked by CORS policy"                          | `CORS_ALLOWED_ORIGINS` doesn't exactly match the frontend's origin (scheme, no trailing slash)      |
| API returns `400 Bad Request` with an HTML page                    | Host not allowed: add the host name to `DJANGO_ALLOWED_HOSTS`                                       |
| The app shows routes without calling the API (no `/api/` requests) | The build has mocks on: set `VITE_ENABLE_MOCKS=false` and redeploy                                  |
| "Can't reach the server"                                           | `VITE_API_BASE_URL` is wrong or missing `/api`; redeploy after fixing (it's baked in at build time) |
| "Could not get data from HERE right now"                           | `HERE_API_KEY` missing or wrong; check the Render logs (`Provider failure: …`)                      |
| First request after a while times out                              | The Render free instance was asleep; retry once it's awake                                          |
